# 架构决策记录（ADR）

记录"为什么这样做"以及"放弃了什么"。每条包含背景、决策、后果与**被否决的方案**——只写好处的决策记录没有价值。

---

## ADR-001：本地优先，云是选项而非前提

**背景**：家庭物品数据的生命周期以十年计。把它交给一个可能停止运营的服务，等于给家庭记忆设了保质期。

**决策**：默认部署在用户自己的设备上；SQLite 单文件即完整数据库；所有功能在断网时可用（除云 AI 识别外）；导出始终可用且完整。

**后果**
- 正面：无网可用、无月费、数据可拷走、隐私边界清晰。
- 负面：备份、升级、HTTPS 的运维责任转移给用户。用 Docker Compose + 一键备份脚本 + 检查清单来抵偿。

**否决**：纯 SaaS。便于集中运维，但违背"数据属于家庭"的前提；且家庭场景没有足够的付费意愿支撑长期运营。

## ADR-002：所有终端必须经过 API，不允许多设备直连同一 SQLite 文件

**背景**：家庭网关最常见的错误做法是把 `homeledger.db` 放在 NAS 共享目录，几台设备分别用本地客户端打开它——看起来"共享"了，实际上是在用网络文件系统模拟本地文件锁。

**决策**：网关只暴露 HTTP API；所有读写经服务端单进程完成；代码与文档中明确写入"不支持多进程/多设备直写 SQLite"。

**后果**
- 正面：事务、审计、权限、并发控制只有一个实现点。
- 负面：网关必须常开；网关宕机时全家不可用（可用定期导出的只读快照兜底）。

**否决**：SQLite + 共享目录。SQLite 的锁是 `flock`/`fcntl` 语义，NFS/SMB 上不可靠，损坏是静默的——等到发现时备份可能已经覆盖了坏数据。

**否决**：每个终端各自一份数据 + 事后同步。冲突解决对普通家庭用户是不可承受的复杂度。

## ADR-003：SQLite 起步，保留 PostgreSQL 适配层，但不假装两者等价

**背景**：需求明确要求"SQLite 起步，保留 PostgreSQL 适配层"，同时警告"不能只替换连接字符串"。

**决策**：
- 统一 ORM 模型与查询，两者共用。
- `DatabaseProvider.capabilities()` 暴露真实差异（`concurrent_writers: false`、JSON 查询能力、推荐场景）。
- 迁移、备份恢复、文档均按方言区分处理；自动恢复对 PostgreSQL 明确报错。

**后果**
- 正面：单机/网关零运维；云端可平滑扩到 PG。
- 负面：能力矩阵需要维护；两套方言的测试覆盖成本存在。

**否决**：只支持一种数据库。要么放弃单机（全上 PG，运维门槛过高），要么放弃云端扩展。

**否决**：ORM 完全屏蔽差异并宣称"无缝切换"。JSON 列、`LIKE` 大小写、日期函数、自增行为都不同，宣称无缝只会在迁移当天爆炸。

## ADR-004：自研轻量迁移器，而非引入 Alembic

**背景**：自托管设备上，迁移必须在无网络、无额外依赖的情况下可预测地执行。

**决策**：`schema_migrations` 表 + 幂等 migration 装饰器 + `python -m app.migrate` 一条命令。迁移列表只追加不修改。

**后果**
- 正面：零额外依赖、输出人类可读、失败可定位、单文件可审计。
- 负面：没有自动 downgrade、没有 autogenerate。迁移数量超过 ~30 个时手工维护成本上升。

**退出路径**：版本表已经存在，迁移到 Alembic 是受控改动，不需要重写业务代码。

## ADR-005：手写序列化，而非自动 ORM dump

**背景**：`warranty_state`、`overdue`、`due_in_days`、`location_path`、`item_count` 都是计算字段。

**决策**：`serializers.py` 手工构造响应字典。

**后果**
- 正面：计算规则只存在于服务端一处；可以按场景裁剪（列表不返回组件，详情才返回）；不会意外泄露 `password_hash` 之类字段。
- 负面：字段增减要手工同步；OpenAPI 文档无法自动描述响应结构（用文档补偿）。

**否决**：`from_attributes=True` 直接 dump 模型。计算字段无处安放，最终会散落到前端各页面，规则必然分叉。

## ADR-006：软删除 + 归档 + 追加式审计

**背景**：家庭场景里"删错了"极其常见，且往往几天后才发现。

**决策**：三种语义分开——归档（退役但仍在册）、软删除（读取路径消失）、硬删除（物理删除，仅管理员）。所有写操作同时写 `item_events`（给人看）与 `audit_logs`（给追责看），两者只追加。

**后果**
- 正面：可追溯、可恢复、可解释"谁在什么时候改了什么"。
- 负面：查询必须处处带 `deleted_at IS NULL`（漏一处就是数据泄露）；表体积随时间增长。

**缓解**：所有列表查询集中在少数几个函数里，过滤条件写成共享表达式而非复制粘贴。

## ADR-007：乐观锁而非悲观锁

**背景**：两个人在两台手机上编辑同一件物品。悲观锁需要长事务或显式租约，在 HTTP 无状态模型下体验很差（"这件物品被锁定，请稍后"）。

**决策**：`items.version` 自增；`PATCH` 可选携带 `version`；不匹配返回 409 并附当前完整记录。`version` 可选，供脚本退化为 last-write-wins。

**后果**
- 正面：无锁等待、无死锁、冲突时可展示"对方改了什么"。
- 负面：客户端需要处理 409；不传 `version` 的客户端会静默覆盖他人修改（已明确为可选择的行为）。

**否决**：悲观锁。家庭网络下客户端可能长时间持锁，导致另一方完全无法操作。

## ADR-008：RBAC + 成员覆盖 + 物品级加性授权

**背景**：固定角色无法表达"这个人能改但不能删""这件药品只给妈妈看"。

**决策**：三层——角色预设、成员级 grant/deny（deny 优先）、物品级 ACL（**只能加性**）。

**后果**
- 正面：无需为每个组合造新角色；权限判定只有一个函数；前后端共用同一份目录。
- 负面：权限来源不直观（排查"他为什么能改"要看三处）；ACL 加性意味着无法用 ACL 隐藏物品。

**否决**：物品级 ACL 支持"限制可见"。会导致仪表盘统计、全量导出、搜索结果的口径与其他成员不一致，且"某件物品凭空消失"对家庭用户是无法理解的故障。

**否决**：为每个家庭自定义角色。需要角色表、角色-权限关联、迁移与 UI，收益远小于成本。

## ADR-009：资产编号、商品条码、序列号三者分离

**背景**：把三者混为一谈是这类产品最常见的建模错误。扫一个 EAN 码就认定"这是唯一一件物品"，在买第二台同型号设备时会立刻崩掉。

**决策**：三个独立字段。资产编号系统生成、永不复用；条码允许重复（同型号多件）；序列号自由录入。扫码接口返回 `matched_by` 与 `ambiguous`。

**后果**
- 正面：同型号多件、二手转卖、条码缺失等真实情况都能表达。
- 负面：用户需要理解三个概念（用 UI 文案与扫码结果的 `hint` 引导）。

**否决**：只用条码作主键。无法处理同型号多件，也无法处理没有条码的自制/老旧物品。

## ADR-010：scrypt + JWT，不引入外部身份服务

**背景**：家庭网关可能永远不联网，不能依赖 OAuth 提供方。

**决策**：`hashlib.scrypt` 做密码哈希（标准库，无需 bcrypt 编译依赖）；PyJWT HS256 签发会话；`users.token_version` 支持强制下线。OIDC 留接口占位。

**后果**
- 正面：零外部依赖、离线可用、改密即全端下线。
- 负面：无 SSO、无 MFA、无密码找回（家庭场景由管理员重置）。

**否决**：bcrypt/argon2。需要编译或额外二进制，在 ARM NAS 上安装体验差；scrypt 在标准库中且参数可调。

## ADR-011：前端不用 UI 组件库

**背景**：自托管产品的首屏体积直接影响"打开快不快"的主观感受；同时需要一套能同时适配桌面三栏与手机底部导航的设计语言。

**决策**：手写 CSS 变量 + 组件样式（约 900 行），手写 SVG 图标约 90 个，单文件按需引用。

**后果**
- 正面：无运行时依赖、体积可控（gzip 后 JS 约 98KB）、视觉统一、暗色主题一处切换。
- 负面：没有现成的表格排序、虚拟滚动、日期选择器；后续新增复杂组件成本高。

**否决**：Ant Design / MUI。体积与样式覆盖成本超过收益，且会让产品看起来像后台管理系统而非家庭应用。

## ADR-012：AI 必须可替换，且默认不外发数据

**背景**：OCR/识别能显著降低录入成本，但把家庭照片上传到第三方是隐私决策，不能由开发者替用户做。

**决策**：`AIProvider` 接口三实现（本地启发式 / 云端 Vision / 关闭）。`describe()` 必须返回 `leaves_device` 与 `privacy_notice`，前端据此显示提示。本地模式不伪造识别结果，明确返回 `needs_review` 与"未安装 OCR 引擎"。

**后果**
- 正面：隐私边界可见、可关闭、可替换；不会出现"以为本地处理其实上传了"的情况。
- 负面：默认体验较弱（本地无 OCR），需要用户主动配置云端才获得完整体验。

**否决**：默认启用云端识别。等于替用户做了数据外发的决定。

## ADR-013：备份用 SQLite 在线 backup API，恢复设三重保险

**背景**：直接 `cp homeledger.db` 在 WAL 模式下会丢失最近提交；恢复是唯一可能一次性毁掉全部数据的操作。

**决策**
- 备份：`sqlite3.Connection.backup()` 生成一致性快照，无需停机。
- 恢复：必须输入 `RESTORE`；自动先做安全备份；覆盖前 `engine.dispose()` + `wal_checkpoint(TRUNCATE)` + 删除 `-wal`/`-shm`；备份文件名用 `O_CREAT|O_EXCL` 原子占位避免同秒撞名。

**后果**
- 正面：热备可用；误操作有回退；不会出现"恢复了但数据是错的"。
- 负面：恢复期间短暂不可用；仅支持 SQLite（PG 走 `pg_restore`）。

**踩过的坑**（保留在此以警后来者）：
1. 不清 `.db-wal` → 旧 WAL 被回放到新库上，数据静默错乱。
2. 不 `dispose()` 引擎 → 池中连接仍指向旧 inode，恢复后读到旧数据。
3. 秒级文件名 → "先备份再恢复"两次操作同名，安全备份覆盖了要恢复的归档。

## ADR-014：通知使用去重键，而不是"发过就不再发"

**背景**：调度器随进程重启、可能被手动触发、多实例时可能重复执行。

**决策**：每条通知带 `dedupe_key = 类型:实体:日期`，唯一索引兜底。周期任务顺延后日期变化，会正常产生新提醒。

**后果**
- 正面：重启不轰炸、双实例不重复、同一任务每天最多提醒一次。
- 负面：同一天内改了任务日期也不会立即重发（可接受）。

**否决**：用"是否已通知"布尔字段。任务周期化后无法再次提醒。

## ADR-015：普通成员默认没有删除权

**背景**：角色预设是一组默认值的判断题。

**决策**：`member` 拥有查看/新增/修改/借还/上传/维护，但**不含** `item.delete` 与 `item.archive`。

**后果**
- 正面：误删代价高、恢复需要管理员介入，默认收紧更安全。
- 负面：小家庭里管理员要频繁代删（可在权限页给某个成员单独 grant，无需改角色）。

**否决**：让 `member` 拥有全部物品权限。删除是不可逆操作里最容易被误触的一个。

## ADR-016：中文界面 + 中文错误文案，其次才考虑国际化

**背景**：目标用户是中国家庭；错误提示的可读性直接决定自助解决率。

**决策**：所有面向用户的文案（含 `detail`、权限名、部署警告、检查清单）用中文直写；不做 i18n 框架。

**后果**
- 正面：文案自然、无翻译腔、开发成本低。
- 负面：支持其他语言需重构文案层（集中在 `permissions.py`、`serializers.py`、`providers/deployment.py`，重构面可控）。

## ADR-017：桌面端复用同一份前后端，不用 Rust 重写业务

**背景**：桌面封装有两条路——把业务逻辑用 Rust 重写一遍以换取"原生"，或者把已有的 Python 服务打包进桌面壳。

**决策**：桌面壳只承担进程生命周期、托盘、窗口，业务仍由同一份 Python 服务、同一份 Web 客户端提供。

**后果**
- 正面：一套业务逻辑、一套数据模型、一套权限；修一处三端同步；桌面端与网关端的数据可以互相搬迁。
- 负面：安装包必须携带 Python 运行时（约 90MB）；启动多一层进程。

**否决**：Rust 重写业务层。桌面端会成为"功能总是落后一截"的第二实现，且权限、并发、迁移逻辑要维护两份——这正是本项目从第一天就在避免的事。

## ADR-018：桌面窗口加载本地 HTTP 服务，而不是打包前端走 IPC

**背景**：Tauri 的常规做法是把前端产物打包进应用，通过自定义协议加载，再经 IPC 调用原生能力。

**决策**：窗口直接导航到 `http://127.0.0.1:<port>`，加载后端托管的同一份 SPA。

**后果**
- 正面：相对路径、`?token=` 图片、标签打印页、路由、Service Worker 全部原样工作，前端零改动；桌面端与浏览器端行为完全一致。
- 负面：页面不再是"受信任的本地页面"，因此拿不到 Tauri IPC——内核能力（托盘、退出、切换模式）只能由启动页使用。这是有意的隔离：业务页面无法触碰文件系统。
- 代价：窗口 origin 随端口变化，见 ADR-019。

**否决**：打包前端 + IPC。需要在 `client.ts` 里引入"当前是否在桌面壳"的分支，图片鉴权、打印页、路由模式都要为 `tauri://` 单独处理，等于维护两套前端运行环境。

## ADR-019：桌面版固定端口 47823

**背景**：`localStorage` 按 origin 隔离。端口变化即 origin 变化，登录态随之丢失。

**决策**：优先绑定 47823；被占用时依次尝试 47824–47832；全被占用才交给系统随机分配（此时用户需重新登录一次）。

**后果**
- 正面：正常使用下重启免登录；端口可预测，便于排查。
- 负面：固定端口与"随便挑个空闲端口"的直觉相反，需要文档解释；端口冲突时体验降级。

**否决**：每次随机端口。技术上更干净，但每次启动都要重新登录，桌面应用的基本体感会被破坏。

## ADR-020：sidecar 用 PyInstaller 单目录打包

**背景**：Python 应用打包有 onefile 与 onedir 两种形态。

**决策**：onedir。

**后果**
- 正面：启动即时（不需要每次解压）；安装包内容可被安全软件逐文件扫描。
- 负面：安装目录里有一个 88MB 的 `_internal` 目录，看起来不如单文件"干净"。

**否决**：onefile。每次启动解压约 70MB 到临时目录，桌面应用凭空多 2–3 秒启动时间，且部分杀毒软件会对"自解压"行为更敏感。

**另注**：PyInstaller 需要解释器带共享库（`Py_ENABLE_SHARED=1`）。pyenv 默认构建不满足，构建脚本会先检测并直接给出可执行的替代方案，而不是让用户去读 PyInstaller 的报错。

## ADR-021：手机端是纯客户端，不做设备端数据库

> **已被 ADR-022 取代。** 这条决策的前提是「同步需要一整套 CRDT/op-log 工程」。
> 实际做下来，记录级 LWW + HLC 已经能覆盖家庭场景，而「手机必须联网才能用」
> 是一个用户每天都会撞上的缺陷。保留原文是为了记住当时为什么犹豫。

**背景**：手机是 HomeLedger 最重要的录入入口——扫码枪不在家里，但手机一直在手上。要不要给手机做本地库？

**决策**：不做。APK 只打包 WebView 和启动页，所有数据请求直接打到家里的网关。

**理由**
- 手机上没有 Python，桌面端的 sidecar 模式不可移植；要让 Python 跑在 Android 上，得换 Chaquopy 之类的方案，产物从 6MB 涨到 60MB，且启动慢一个数量级。
- 真要做本地优先，问题不在"能不能存"，而在"多端改了同一件物品怎么办"。这需要同步引擎（op-log 或 CRDT）、冲突可视化、离线队列重放——那是整个项目里最贵的一块，不该作为"顺手加个 APK"的副产品出现。
- 家用场景的可用性约束很弱：网关在客厅，手机在卧室，同一个 Wi-Fi。真正断网的时刻，用户也不在乎能不能改物品备注。

**后果**
- 正面：APK 只有 6.6MB，安装即用；没有第二份数据，也就不存在"手机上改了电脑上看不到"的困惑。
- 负面：网关关机或不在同一网络时，手机端不可用。UI 需要把这件事说清楚（首次启动就是网关地址表单，而不是一个会转圈的错误页）。
- 负面：`boot()` 在移动端不启动任何进程，桌面端的托盘、单实例、数据目录等能力必须编译期剔除，否则会在真机上以"找不到路径"的形式失败。

**否决**：把桌面端的 sidecar 原样塞进 APK。技术上可以（Chaquopy / 交叉编译 CPython），但会把一个 6.6MB 的客户端变成 60MB+，换来的只是"断网也能改备注"，不划算。

**否决**：只做 PWA 不做 APK。PWA 能覆盖 90% 的场景，但 iOS 上的存储会被系统清理，Android 上的扫码权限也更受限制。壳的成本很低（这份代码就是），先给一个能装的东西。

## ADR-022：所有设备内置本地库，服务器降级为同步会合点

**背景**：原先的模型是「服务器 = 数据库，客户端 = 视图」。桌面端因为自带 sidecar 而侥幸能离线，手机和浏览器不能。用户的要求很直接：所有设备都要能离线用，设置里能切本地或服务器，同步要加密。

**决策**：每台设备都有完整副本，所有读写先落本机。服务器的职责缩减为三件事：按序分发变更、存放密文附件、保存被口令包封的数据密钥。

**理由**
- 「手机必须有网才能改备注」不是可接受的降级，是每天都在发生的失败。
- 一旦客户端持有完整数据，服务器就没有理由再参与业务校验——它连字段都读不懂。
- 反过来说，也意味着**不能再指望服务端做权限控制**。本地模式下权限就是设备本身；域模型里的角色和细粒度权限只有 `remote` 模式和未来的多人共享场景才真正生效。

**后果**
- 正面：断网可用；局域网抖动不再表现为「转圈」；服务器可以小到一台树莓派。
- 负面：两套数据路径（本地引擎 / 直连服务端）必须保持 API 形状一致，否则页面会在切换模式时崩。这是 `frontend/src/local/handlers.ts` 每个函数都对着一个 Python 路由写的原因。
- 负面：服务端的那 127 个测试覆盖不到本地引擎；本地引擎的正确性靠浏览器内端到端测试保证。

**否决**：让手机跑 Python sidecar（Chaquopy）。产物从 6 MB 涨到 60 MB+，启动慢一个数量级，只为了复用一套已经跑在浏览器里的逻辑。

**否决**：只做「读缓存 + 写队列」。那样离线时不能新建物品、不能改位置，用户体验上是「只读」，不是「可用」。

## ADR-023：冲突用记录级 LWW + 混合逻辑时钟，不做字段级 CRDT

**背景**：多端离线编辑必然冲突。可选方案从「后写覆盖」到「每字段一个时钟的 CRDT」都有。

**决策**：每条记录一个 HLC，服务器保留最高者；落败的一方在同一个响应里拿到胜者并立刻采纳。

**理由**
- 家庭场景的冲突率极低：同一件物品在同一分钟被两个人编辑，是例外而非常态。
- 字段级合并需要为每个字段维护时钟、定义字段级删除语义、处理「数组字段怎么合并」，复杂度是记录级的十倍以上。
- HLC 而不是纯时间戳，是因为手机时钟会漂：物理部分保证可读与大致有序，逻辑计数器保证因果不倒挂。

**后果**
- 正面：协议足够小，Python 和 TypeScript 两份实现都能在一屏内读懂。
- 负面：A 改价格、B 改位置，最终只留一个人的改动。审计日志里能看到两次修改，但用户需要手动补。
- 负面：`resolved` 回传让「保存成功」的语义变成「保存成功，但可能被别人的版本覆盖」——UI 必须在冲突时给出提示，不能默默吞掉。

**否决**：CRDT（Automerge/Yjs）。为几千条家庭记录引入一个 200 KB 的 CRDT 运行时和一堆不可读的二进制状态，收益与成本不匹配。

## ADR-024：字段级明文/密文分层，而不是整条记录加密

**背景**：服务器如果什么都读不到，就无法为新设备提供「输入口令前的列表」，也无法做任何索引；如果什么都读得到，端到端加密就是一句空话。

**决策**：每条记录拆成 `meta`（明文：名称、编号、分类、位置、状态、数量、时间戳）和 `secret`（密文：价格、序列号、描述、购买渠道、备注）。附件全部加密。

**理由**
- 「新设备配对后立刻看到东西」是有价值的：用户能确认自己连对了家庭，而不是面对一个空屏。
- 名称和位置的低敏感度是产品判断，并且提供了 `strict` 开关让用户推翻它。
- 分层让服务器在不解密的前提下完成分发、去重、配额，这是它唯一需要的智能。

**后果**
- 正面：服务器代码里没有一行解密逻辑，审计起来很容易。
- 负面：`meta` 里的名称对服务器可见。这是明确告知用户的取舍，不是隐藏行为。
- 负面：`strict` 模式下新设备在解锁前只能看到空列表，需要 UI 提示「输入口令后显示」。

**否决**：整条记录加密 + 服务器只存 blob。那样每次同步都要全量拉取再本地比对，游标机制失去意义。

## ADR-025：桌面窗口加载打包前端，sidecar 退居「局域网服务」

**背景**：ADR-018 让桌面窗口加载 `http://127.0.0.1:47823`，好处是同源、无需 CORS、复用整套 Web 前端。但引入本地库之后，这个决定产生了一个新问题：IndexedDB 是按 origin 隔离的，端口一旦回退到 47824，用户的整个书库就「消失」了——数据还在，但页面看不到。

**决策**：窗口加载打包进二进制的 SPA（origin 固定为 `tauri://localhost`），sidecar 仍然启动，但只承担「让局域网里其他设备连进来」的角色；它启动失败不再阻塞界面。

**理由**
- origin 稳定是本地存储的前提，端口回退是不可控的外部条件。
- sidecar 失败从「整个应用打不开」降级为「局域网共享不可用」，这是正确的爆炸半径。
- 桌面端从此和手机端走完全相同的代码路径，少一类只在桌面出现的问题。

**后果**
- 正面：桌面端启动不再依赖 Python 进程；sidecar 崩溃只是托盘里少一个能力。
- 正面：本地数据与端口无关，47823 被占用也不影响。
- 负面：`tauri.conf.json` 的 `frontendDist` 指向 `backend/app/static`，编译前必须先构建前端；`generate_context!` 在目录不存在时直接失败。
- 负面：托盘里的「立即备份」仍然走 sidecar 的 `/desktop/backup`，没有 sidecar 时不可用；应用内的「导出快照」是替代路径。

**否决**：把 sidecar 从安装包里去掉。它在「一台常开的机器当家庭服务器」这个场景里仍然是最省事的方案，只是不该挡在桌面端自己的启动路径上。

## ADR-026：桌面端可以当家庭服务器，但默认不监听局域网

**背景**：用户要的「通过加密连接同步到服务器」在家庭里有个前提问题——服务器从哪来。ADR-025 之后 sidecar 还活着，却只听 `127.0.0.1`，对家里其他设备毫无用处，等于 88 MB 的死重量；而要求每个家庭先买 NAS 或租云主机，是把一个产品问题推给用户。

**决策**：给 sidecar 一个 `--host 0.0.0.0` 选项，由桌面端配置 `lanShare` 控制；默认 `false`（只听回环），用户在「设置 → 同步」里点一次按钮才打开。打开时重启 sidecar，接口地址和 `http://192.168.x.x:端口` 一起返回给前端。

**理由**
- 「同一 Wi-Fi 下能被访问的端口」不该是默认值。咖啡馆、宿舍、公司网络都是局域网，用户没做过这个选择。
- 一旦打开，数据仍然是端到端加密的：服务器上 `meta` 是明文索引，`secret` 和附件是密文，中间人拿到流量也读不出序列号和照片。所以风险边界是「别人能看到登录页」，不是「别人能读到你的东西」。
- 默认关闭 + 一次点击 + 明确文案，比一个埋在设置深处的复选框更容易被理解。
- CORS 需要同时放行 `tauri://localhost`（桌面 SPA）和 `http://tauri.localhost`（手机 WebView），否则窗口连自己启动的服务都会被浏览器拦掉；局域网模式下再追加本机所有 IPv4 的该端口。

**后果**
- 正面：只有一台电脑的家庭开箱即可多设备同步，不用 Docker、不用云。
- 正面：`deb` 里的 88 MB sidecar 从「用不上的负担」变成「默认不启用但随时可用的能力」。
- 负面：切换开关会重启 sidecar（约 1 秒），期间局域网请求会失败。
- 负面：`_local_ipv4s()` 用 UDP 路由探测取地址，多网卡机器可能只报告主网卡；用户仍可手填正确的 IP。

**否决**：默认监听 + 文档里写「可以关」。默认值就是产品对「大多数人的情况」的判断，把它设成一个需要用户去关的危险状态，等于把安全问题转嫁给没读文档的人。

## ADR-027：加入已有家庭时按名字合并目录，而不是清空或复制

**背景**：两台设备各自从同一份种子清单开始用，之后才通过服务器连到一起。拉取会把服务器的分类/地点写进本地，但两者 id 不同、名字相同，于是每个下拉框出现两个「厨房」。而「清空本地目录」会让已有物品失去归属。

**决策**：`linkServer` 在拉取**之前**记录本机目录行的 id；拉取之后调用 `store.mergeDuplicateCatalog()`，按「同表 + 同名 + 同父节点」找对手，保留服务器来的那条，把引用改指过去，本地那条物理删除（不进 outbox），然后才推送。

**理由**
- 必须在拉取前取快照：`applyRecords` 给所有落地记录盖上本机 `family_id`，之后无法从数据本身区分来源。
- 物理删除而非墓碑：本地那条从未上传，墓碑只会向服务器广播一个它不认识的 id，白白制造一条垃圾记录。
- 先合并再推送：否则重复项会写进服务器，再发给家里每一台设备，变成所有人的问题。
- 名字是用户唯一能感知的身份。「厨房」和「厨房」在语义上就是同一个地方，按 id 保留两份是把实现细节暴露给用户。

**后果**
- 正面：设备先离线用、后加入家庭，是很自然的路径，现在这条路径不会留下烂摊子。
- 负面：用户自己改过名的分类不会被合并（名字不同视为不同分类），这时两份都保留——这是保守但可解释的行为。
- 负面：合并只做一层父子匹配，深层嵌套的同名结构可能匹配不到，需要手动整理。

**否决**：按 `sort_order` 或创建时间保留本地版。服务器上的那条已经被其他设备引用，换成本地 id 等于让别人的物品指向不存在的分类。

## ADR-028：二维码指向服务器的随机 token，而不是物品编号

**背景**：贴纸印出来就贴到实物上了。撕下来会留胶，重贴要重新找位置。所以二维码里编的东西，必须比「当前这台服务器、这个端口、这个 App 版本」活得久。最初的实现是 `homeledger://scan?code=HL-000123`：扫的人必须先装 App，换端口就整车报废，而且把物品编号公开写在码里——拍一张就知道这家人有多少件东西、编号排到多少。

**决策**：二维码内容是 `<服务器地址>/api/v1/public/q/<随机 token>`。服务器提供一张服务端渲染的只读页面，手机自带相机扫开即可查看，不需要 App。token 用 `secrets.token_urlsafe(16)` 生成，按 `item_id + base_url` 复用；可以单件作废重签。

**理由**
- 扫的动作发生在**别人的手机上**。要求对方先装一个 App，等于要求每个来家里帮忙的人先注册。
- 编号是内部标识，token 是能力凭证。二者的区别在于：泄露编号只是信息泄露，泄露能力要能撤销。
- 服务端渲染 HTML 而不是返回 JSON 再让前端画：从扫码到看见内容只有一次请求，弱网下不会先白屏再补数据。也不需要引入任何前端框架。
- 链接指向服务器而不是 App，意味着「换手机」「重装系统」「换 App」都不影响已经贴在冰箱上的纸。

**后果**
- 正面：任何手机、任何系统、不装任何东西，扫了就能看。
- 正面：换端口/换主机名会签新链接，旧贴纸仍能打开（指向旧地址）；只要服务器地址不变，重复打印不产生新 token。
- 负面：二维码只有在内网可达时才有用。出门在外扫码打不开——这是设计意图，不是缺陷，见 ADR-030。
- 负面：`items.qr.png` 与 `labels/*` 的行为从「纯本地生成」变成「需要服务器签发 token」。本地模式下前端退回用 `homeledger://` 深链并在界面上说明原因，而不是给一张扫了没反应的图。
- 负面：多了一个表（`qr_links`）和一套 token 生命周期，撤销需要审计记录（`item.qr.revoke`）。

**否决**：把物品编号加密后编进二维码，扫码时本地解出。加密只能隐藏内容，不能撤销；贴纸一旦贴出去就永久有效，而这个码印在纸上是会被人拍照的。

## ADR-029：查看页静默待机，用租约而不是常驻进程

**背景**：ADR-028 之后，服务器多了一个「任何人扫一下就能访问」的入口。如果它常驻一套模板缓存、一个后台线程、一份统计，那么在一个跑在 NAS 或旧笔记本上的家庭服务器里，这是纯浪费——大部分时间的扫码次数是零。

**决策**：`QrGateway` 用一个全局单例管理租约。扫码时 `wake(token)` 建立 90 秒租约并把渲染好的 HTML 放进 LRU 缓存（上限 64 条）；页面内脚本每 5 秒 `POST /public/q/{token}/beat` 续租；心跳停了租约过期，缓存丢弃，后台线程退出。没有租约时它不持有任何东西。

**理由**
- 家庭服务器最常见的形态是一台常年开机但不快的机器。为「一天扫三次」常驻线程和缓存不合算。
- 租约比「访问后 N 分钟清理」准确：有人在看就一直醒着，人走了就睡，不需要猜。
- 缓存的是渲染结果而不是数据库查询结果——省掉的是模板渲染和 N+1 查询，这两件才是扫码页的主要开销。
- 上限 64 条是防脚本刷的保护，不是容量规划。一家人同时扫 64 个码不存在。

**后果**
- 正面：空闲时零内存、零 CPU；`/system/qr` 能看到 `state/viewers/next_sleep_in`，行为可观测而不是「据说很省」。
- 正面：租约过期后缓存丢弃，物品改了名字不会有人看到 90 秒前的旧页面。
- 负面：进程内的单例意味着多 worker 部署时每个 worker 各管一份租约，`views_total` 之类是近似值。家庭规模下无所谓，已在文档里写明。
- 负面：页面必须带 JS 发心跳。禁用 JS 的浏览器能看内容，但服务器会在 90 秒后认为没人看。可接受——页面本身不需要 JS 才能读。

**否决**：常驻一个内存缓存 + TTL。省下的那点代码换来的是「服务器永远醒着」，而这正是要避免的。

## ADR-030：内网限制按来源地址判断，失败时不确认 token 是否存在

**背景**：扫码页是唯一不需要登录的读取入口。用户的要求是「仅限连了家庭 WiFi 内网时才能查看」——这是访问控制，不是加密。

**决策**：在 `GET /public/q/{token}` 上按 `request.client.host` 判断：`ipaddress` 的 `is_private / is_loopback / is_link_local` 之一才放行；否则返回 403 和一张「仅限家庭内网访问」的页面。**这张页面和不存在的 token 返回的页面完全相同。**

**理由**
- 用 `ipaddress` 而不是字符串前缀。`10/8`、`192.168/16` 好判断，`172.16/12` 的边界、`100.64/10` 的运营商级 NAT、IPv6 的 `fc00::/7`，手写前缀迟早漏一个。
- 区分「token 无效」和「你不在家」等于给外网扫描者一个存在性预言机：拿一个字典跑一遍，就能知道哪些 token 是真的。哪怕只是 403 和 404 的差别，也足够。
- 反向代理场景下 `request.client.host` 是代理的地址。这是**正确**的保守行为：代理如果在同一台机器上，它本身就是内网；如果代理在公网，系统就不该认为请求来自内网。要放开必须显式配置代理信任，而不是默认相信 `X-Forwarded-For`——那个头谁都能伪造。

**后果**
- 正面：外网拿到 token 也打不开，且无法用它探测别的 token。
- 正面：`HOMELEDGER_QR_LAN_ONLY=false` 可以关掉这个限制（比如套了公网 TLS 又想给亲友看），关的时候 `/system/qr` 会明说访问范围。
- 负面：docker 里跑、前面套了 nginx 时，容器看到的来源是网桥地址（私网），限制实际不生效。此时安全性依赖网络层，文档里写明。
- 负面：IPv6 用户如果拿到的是公网地址段，会被拒绝。现实里家庭宽带拿到的通常是 `fd00::/8` 或 NAT 后的 IPv4。

**否决**：用 `X-Forwarded-For` 判断来源。它由客户端提供，伪造成本为零。默认信任它等于把这道闸门做成装饰。

## ADR-031：全屏是尽力而为的，安全区是布局的一部分

**背景**：手机端要「打开就全屏，状态栏别占地方」。安卓的沉浸式需要主动申请（`WindowInsetsControllerCompat.hide`），但结果不由应用决定：有的系统在用户从边缘上滑时会强制把状态栏拉回来，有的厂商 ROM 会忽略，分屏和多窗口更是直接失效。如果布局假定「状态栏一定没了」，那么拿不到全屏的机器上，顶栏会被状态栏压掉半行。

**决策**：原生侧用 `WindowCompat.setDecorFitsSystemWindows(window, false)` + `hide(statusBars())`，并在 `onWindowFocusChanged` 里重新隐藏一次（切回来之后系统会把栏放出来）；同时设 `LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES`，让内容能用刘海两侧的区域。前端不做任何判断，只用 `env(safe-area-inset-top)` 给顶栏留内边距。

这样得到双态自适应：全屏生效时 inset 为 0，顶栏贴到屏幕顶端；全屏没生效时 inset 等于状态栏高度，顶栏自动让开。**同一份布局覆盖两种结果，不需要运行时检测。**

**理由**
- 「检测是否全屏成功再切布局」需要一次异步查询，而查询和绘制之间有窗口期，会闪一下。
- `env(safe-area-inset-*)` 是系统给的答案，不是猜的。它同时覆盖刘海、挖孔、圆角、手势条四类硬件差异。
- 用户从边缘上滑把状态栏唤回来是**系统的**手势，不是应用能拦的。硬拦会让人没法看时间和通知。
- 下拉刷新、输入法、横屏都走同一套 inset，不用为每个场景写一遍。

**后果**
- 正面：全屏成功与否都不会压掉内容，也不会在顶栏上方留一条突兀的空白。
- 正面：iPhone 的刘海和安全区用同一套 CSS 处理，不需要 `@supports` 分支。
- 负面：`env()` 需要 `viewport-fit=cover`，漏了它就是 0，看起来「安全区没生效」。已在 `index.html` 和扫码页模板里都写上。
- 负面：安卓上 `onWindowFocusChanged` 每次切回都隐藏一次状态栏，用户如果正好想下拉看通知，会觉得「它又没了」。这是沉浸式的固有摩擦。
- 负面：`BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` 依赖系统版本，老设备上小概率需要点两下屏幕才能唤出状态栏。

**否决**：拿不到全屏就把窗口缩小（用户提过的备选）。在一个已经有系统栏的屏幕上再缩一圈，等于同时损失两次空间。

## ADR-032：连不上服务器是一个页面，不是一片白

**背景**：桌面端的 WebView origin 是 `tauri://localhost`，这不是一个 http 源。切到「直连服务器」模式后，`fetch("/api/v1/...")` 里的相对路径会打到 WebView 自己的资源处理器，而不是用户填的服务器——请求失败，`loading` 永远为真，屏幕上一片白。用户看到的是「除了本机模式其他都打不开」。

**决策**：三层防护。

1. **地址必须显式**。remote 模式没有保存过服务器地址时，`api()` 直接抛 `ApiError(0, "还没有填写服务器地址")`，不再发一个注定失败的相对请求。
2. **连接失败是一等状态**。`auth.load()` 在 remote 且未登录时先探一次 `/system/info`，只有**网络层**失败（`status === 0`）才置 `connectionError`；401/403 这类业务失败照常走登录流程。`ConnectionGate` 在路由之前判断，把「连不上」渲染成连接页而不是空仪表盘。
3. **兜底不白屏**。`ErrorBoundary` 包住整个路由树，React 渲染异常给出三个出口（重试 / 重新加载 / 改用本机模式）。

连接页本身带指数退避自动重试（3s→30s）、`online` 事件触发重试、以及「改用本机模式」的逃生门。

**理由**
- 白屏是**没有信息**的失败。用户无法区分「在加载」「连不上」「崩了」，只能反复重启。
- 区分网络失败与业务失败是关键：401 说明服务器活着，把人送到登录页是对的；`status === 0` 说明根本没连上，送去登录页只会让人输完密码再失败一次。
- 连接页要保留已经填过的地址。重试时不该让用户重新输入一遍。
- 逃生门必须显眼。本机模式的数据一直都在，用户只是被一个连不上的服务器挡住了。

**后果**
- 正面：四种失败（没地址 / 地址不可达 / 服务在但数据库挂了 / 前端崩了）都有明确界面和出口。
- 正面：所有请求带 15 秒超时（手写 `AbortController`，不用 `AbortSignal.timeout`——旧 WebView 没有）。
- 负面：多了一次探活请求。省掉它的代价是首屏多等一个超时周期。
- 负面：`serverStore` 需要区分「打包应用」和「浏览器」：浏览器的 `location.origin` 就是服务器，打包应用的不是。这段判断分散在 `isTauri()` 里，改动时要一起看。

**否决**：在 WebView 里注册自定义协议，把 `/api` 转发到用户填的地址。改的是 WebView 的请求路由，调试时所有网络面板都失去意义，而且和 CORS 的交互很难说清。

## ADR-033：下拉框自己画，接受失去系统选择器

**背景**：分类、位置、状态这些字段原本用 `<select>`。在桌面浏览器上它长得还行，但打包后的 App 跑在 WebView 里，安卓展开的是一张**独立的系统单选列表**——全屏白底、系统字体、42px 行高、没有品牌色。它从已经画好的「新增物品」弹窗里弹出来，用户看到的是两个应用叠在一起。这不是审美偏好：同一个流程里，一个控件突然换了一套视觉语言，人会以为跳出了当前页面。

**决策**：`components/ui.tsx` 里实现 `Select`，18 处原生下拉全部替换。移动端（≤860px）是底部抽屉，与 Modal 共用圆角 / 阴影 / 遮罩，48px 行高；桌面是锚定触发器的浮层，下方放不下就向上翻。选项超过 10 个出现搜索框。键盘 ↑↓ / Enter / Esc，`role="listbox"` + `aria-activedescendant`。手机键盘弹起时用 `visualViewport` 把抽屉上移。顺带把 8 处 `window.confirm` 换成 `useConfirm()`——同一个问题：样式由系统决定，而且部分 WebView 里它根本不弹窗，直接返回 `false`，于是「清空数据库」这类按钮点下去毫无反应。

**理由**
- 原生 select 在安卓上**没有中间态**：要么收起，要么整屏。在表单中间弹一张全屏列表，上下文全丢。抽屉至少留了上面的表单和遮罩，人知道自己在哪。
- 选项需要携带额外信息：分类的色点、物品的编号、角色的权限说明。`<option>` 只能放纯文本，这些信息要么丢掉，要么拼进字符串变成「厨房（12）」这种。
- 搜索是硬需求。维护任务要从几百件物品里挑一件，原生 select 只能靠滚动；移动端首字母跳转对中文无效。
- 一致性可以量化：抽屉与 Modal 用同一组 `--radius-lg` / `--shadow-lg` / 遮罩色。原生控件做不到，因为它的样式由系统决定，改不了。

**后果**
- 正面：一套视觉贯穿到底，深浅色主题都跟着走；搜索、色点、编号、键盘导航都在。
- 正面：`aria-activedescendant` 的朗读结果比原生 select 更准——读屏会念出「厨房，已选中，3 之 5」。
- 负面：**失去了系统的惯性滚动、滚轮选择、「取消 / 确定」按钮**。iOS 用户习惯了底部滚轮，抽屉是另一套肌肉记忆。
- 负面：必须自己处理键盘遮挡。`innerHeight` 不会因为键盘而改变，只有 `visualViewport` 能拿到真实可视高度——这条没在 iOS Safari 上验过（见 MOBILE.md 第 7 节）。
- 负面：浮层的定位要跟着滚动和 resize 重算。用 `position: fixed` + 捕获阶段的 `scroll` 监听解决，但多了一层需要维护的代码。
- 负面：18 处调用点都要把 `<option>` 改写成 `options` 数组，改错一处就是「选了没反应」。已全部替换并用 `grep '<select'` 守住（现在只剩注释里那一处）。

**否决**：用 `<select>` 但加 `appearance: none` 自定义外观。那只改了收起时的样子，展开后的列表仍由系统绘制——问题恰恰出在展开的那一瞬间。

## ADR-034：相机预览让 `<video>` 常驻；"改了没生效"用构建指纹回答

**背景**：两个 bug 同时到了手上，看起来无关，其实是同一类问题——**状态和它依赖的 DOM 不在同一个时刻成立**。

1. 扫码页拿到相机权限、相机指示灯亮着，但取景框全黑。代码是「`getUserMedia()` → `videoRef.current.srcObject = stream` → `setCamOn(true)`」，而 `<video>` 只在 `camOn` 为真时才渲染。执行到第二行时组件还没重新渲染，`ref.current` 是 `null`，赋值被 `if` 跳过去了；等 `<video>` 挂出来，那一次赋值已经过去了，没有人再补。用户看到的是"权限给了、相机开了、黑的"。
2. 下拉框改成自绘之后，有人装上新包仍然看到系统列表。查代码没问题、查产物没问题——因为跑的是更早那一次安装。**没有任何地方能让用户（或我们）一眼确认"这台设备上是哪一次编译"**。

**决策**

- `<video>` 移出条件渲染，常驻 DOM；不开相机时 `opacity: 0`，绑流不再依赖渲染时序。
- `play()` 之后追加 `waitForFirstFrame()`：轮询到 `videoWidth > 0 && readyState >= 2` 再开始解码。Android WebView 会在 `play()` resolve 后若干帧仍报 `readyState = 0`，此时 jsQR 读到的是空画布，症状和黑屏一样。
- `getUserMedia` 的失败按 `name` 分开说：拒权 / 没摄像头 / 被占用 / 非安全上下文。统一一句"无法启动相机"等于什么都没说。
- 每次构建生成指纹 `YYYYMMDD-HHmm`，注入 `__BUILD_ID__`，写进 `<html data-build>`，显示在登录页页脚和「我的」底部；服务端版本与界面版本不一致时，设置页直接给一行黄字提示。
- `index.html` / `sw.js` 返回 `Cache-Control: no-cache`；`/assets/*` 因为文件名带内容哈希，给 `immutable`。Service Worker 的缓存名跟着构建指纹走（原来固定 `hl-v1`，清理分支永远不触发，旧壳可以赖在手机上半年），注册时 `updateViaCache: "none"`，新 worker 接管后自动刷新一次。

**理由**
- 用「等一帧再渲染」这类补丁绕开时序问题，会把 bug 藏进更深的层次；把 `<video>` 常驻是从结构上消掉这个时序，不需要任何 `setTimeout`。
- 构建指纹比版本号有用：同一个 1.0.1 可能被打过五遍，版本号区分不了，指纹可以。它把"是不是装错包"从一次十分钟的排查变成一次对视。
- Service Worker 的缓存名如果不由构建决定，那它就是一个只进不出的黑洞：`activate` 里那段"删掉不匹配的缓存"永远匹配，永远不删。

**后果**
- 正面：扫码从"黑屏"变成"能扫"——390×844 的移动视口 + 假摄像头喂一段二维码视频，识别到 `HL-000001` 并查到物品，全程无 console 错误。
- 正面：`document.documentElement.dataset.build` 可以在控制台直接读，支持远程问一句"你那行写的是什么"。
- 负面：`<video>` 常驻意味着即使不开相机，页面上也挂着一个解码器元素。实测没有可感知开销（没有 `srcObject` 时它不解码任何东西），但这是一条需要记住的约束：**不要**再把它包进条件渲染里图省事。
- 负面：`waitForFirstFrame` 最长等 6 秒。摄像头真的坏掉时，用户要等 6 秒才看到提示。接受——比起"永远黑着且不说话"，6 秒后给一句人话更好。

## ADR-035：本机模式的路由是手写分段匹配，删除只走 `store.remove()`

**背景**：备份能创建、能下载，就是删不掉。远程模式删得掉，只有手机和桌面上不行。

`frontend/src/local/handlers.ts` 是所有本机请求的唯一入口。它不用框架，靠一行
`const parts = path.split("/").filter(Boolean)` 和手写的 `if` 分支来路由。备份删除那一条写成了：

```ts
if (parts[0] === "system" && parts[1] === "backups" && parts.length === 4 && method === "DELETE") {
  store.tables.backups.delete(decodeURIComponent(parts[2]));
  return { ok: true };
}
```

三个错误，任何一个都足以让它失效：

1. 路径是 `/system/backups/<filename>`，**三段**，不是四段。条件永远不成立，请求一路掉到末尾的 `throw new ApiError(404, "本机模式暂不支持该操作")`。
2. `parts[2]` 是文件名（`homeledger-2026-…json`），而表的主键是 uuid。就算分支命中，`Map.delete(filename)` 也删不到任何一行。
3. 即使 id 对了，直接操作 `tables` 这个 `Map` 也不落盘、不写墓碑、不标脏。刷新一次页面（IndexedDB 重新载入）记录就复活。

而前端 `del()` 抛出的错误没有人接：`ConfirmDialog` 的 `onConfirm` 是 async，`onClose()` 在它返回前就执行了。于是用户看到的是**弹窗关闭、列表不变、没有任何提示**——比报错更难查。

**决策**

- 分段判断必须和真实路径对齐；新增分支时把完整路径写在注释里，别只写 `length`。
- 删除一律用 `store.remove(table, id)`，它负责墓碑、HLC、脏标记和 outbox。直接 `tables[x].delete()` 是禁止的。
- 本地 handler 的写操作补上 `audit()`，与后端 `record()` 对齐。
- 前端的异步确认操作统一 `try/catch` + toast；`deleteTarget` 在 `onConfirm` 开头先取出来，因为 `onClose` 会立刻把它置空。
- 后端 `DELETE /system/backups/{filename}` 容忍文件已不存在：记录照样删，返回 `file_removed: false`。以前这里 404，导致「手动清过备份目录」的家庭永远留着一行删不掉的僵尸记录。
- 本机备份的文件名必须唯一。时间戳只到秒，连点两次「立即备份」会撞名——两条记录同名，删除时按文件名找到的可能是另一条。服务器端用 `O_CREAT|O_EXCL` 抢名字，本机没有文件系统可用，按同样的规则补 `-2`、`-3` 后缀。

**理由**

- 路由表是手写的，就没有框架替你检查路径——**唯一可靠的办法是让真实请求跑一遍**。这次就是靠 Playwright 的一条 `DELETE` 才看见 404。
- 直接改 `Map` 看起来"更简单"，但它绕过的是整个本地优先模型：墓碑、时钟、同步队列。省下的三行会在下一次刷新时连本带利还回来。
- 文件丢了还坚持 404，是把「文件系统的事实」和「数据库的事实」混为一谈。用户要的是"这条记录消失"，不是"文件必须存在"。

**后果**

- 正面：本机模式删备份立即生效，刷新后不复现；远程模式在文件被手动删掉后也能清掉记录。
- 正面：`{"ok":true,"file_removed":false,"record_removed":true}` 这组字段让调用方知道到底删掉了什么。
- 负面：本机模式删的只是记录。文件在系统下载目录里，浏览器没有句柄，删不了。**界面上必须说清楚**（确认框里现在写了），否则用户以为磁盘空间回来了。

## ADR-036：批次单独建表，到期状态算出来，数量不回写

**背景**：需求矩阵里最后一项 `⚠️ 部分` 是"批次库存"——此前只能用「数量 + 组件 + 自定义字段」近似。
食品、药品、耗材这类东西的真实形态是：同一件物品分几次买，每次的到期日不同，
有时还分开存放（厨房柜子 vs 冰箱）。

### 决策一：批次是独立的表，不是 `items` 上的几个字段

**否决：在 `items` 上加 `expires_on` / `batch_no`。** 一个物品只有一组日期，
表达不了"这批 11 月 3 号过期、那批 12 月 20 号过期"。退一步说"取最早的那个"，
对其余几批就是错的：它们还没到期，界面却一直标红。

**否决：把每个批次建成一个独立 `item`，再用 `item_components` 关联。**
这样每批都有一整套物品字段（分类、位置、保修、二维码、维护计划），
账本会从"1 件酸奶"变成"5 件酸奶"，物品总数、登记价值、扫码结果全部失真。

**选择：`item_batches` 表**，一个物品对多行。每行有自己的批号、数量、
生产日、到期日、存放位置、来源。

### 决策二：到期状态是计算值，不落库

`expiry_state`（`none`/`fresh`/`expiring`/`expired`）与 `days_left` 在序列化时按
**当天日期**算出。

**否决：存一列 `status`，用定时任务每天刷新。** 这样系统里就多了一个"必须跑起来
才正确"的字段：任务挂了、设备离线一周、手机在本地模式下根本没有调度器——
状态就停在错误的那一天。而算出来的状态永远不会过期，也不需要迁移去修历史数据。

代价是每次读都要算一次。一个家庭几百个批次，这点算术比不上一次 IndexedDB 读。

### 决策三：批次数量不回写 `items.quantity`

**否决：`quantity = sum(batches.quantity)`。** 看着"更一致"，实际是把用户填的账面值
交给一串流水去覆盖。用户在物品表单里写"6 盒"、只登记了 2 盒的批次，一保存就变成 2——
这不是修正，是销毁。而且没建过批次的家庭（绝大多数）会突然发现数量不可编辑了。

**选择：两者独立保存，不一致时提示差额**：
「批次合计 5 盒，物品登记数量 6 盒。两者独立保存，不会互相覆盖。」
让用户自己决定是补一批、还是改总数。

### 决策四：复用 `item.*` 权限，不新增 `batch.*`

批次是物品的属性，不是独立域。新增 4 个权限要同时改 `permissions.py` 的四张表、
角色预设、前端 `seed.ts` 的镜像和成员页，为的是表达一个没人提过的诉求
（"能改物品但不能改它的批次"）。能看物品的人就该看到它的批次。

**后果**

- 正面：一个物品可以有任意多个批次，各带各的到期日；临期提醒进首页、告警条和提醒中心（`batch_expiring`）。
- 正面：同步把日期放进 `secret` 层，服务器仍然不知道你家的东西什么时候过期。
- 负面：物品数量与批次合计可能长期不一致，靠界面提示而不是约束。这是有意选择的"提示而不代劳"。
- 负面：本机模式没有调度器，所以**站内通知只在有服务器时产生**；本机模式靠首页卡片和物品页徽章，这两处不依赖调度器。

## ADR-037：实时推送用 SSE，只推「变了什么」，鉴权走请求头

**背景**：两个人同时用一个家庭账本时，A 保存了，B 的页面不会变——远程模式根本没有
任何刷新机制，本地/同步模式靠 60 秒一次的轮询。B 会以为 A 没保存，或者自己刷新一下
才发现东西已经改了。

### 决策一：SSE，不是 WebSocket

**否决：WebSocket。** 我们只需要服务器 → 客户端的单向通知，一条消息几十字节，
一小时可能一条也可能几百条。WebSocket 换来的是双向通道、自定义心跳、握手升级，
以及"某些反代要单独配置 Upgrade 头"这一整类部署问题——全是这个功能不需要的。

**选择：Server-Sent Events。** 它就是一条不结束的 HTTP 响应，能穿过现有反代和鉴权，
断线由客户端重连，nginx 只要关掉缓冲就能用。代价是单向——而单向正是我们需要的。

### 决策二：只推提示，不推数据

**否决：把变更的行内容一起推下去。** 一旦推数据，就要回答：字段级还是行级？顺序怎么保证？
丢了一条怎么办？收到时本地已经有更新的版本怎么办？——这些问题的答案合起来就是一个
同步协议，而这个项目已经有一个（`sync/engine.ts`），不需要第二个更差的。

**选择：推 `{"entities":["item"],"action":"item.update"}`，客户端自己重新请求。**
好处是这条通道**可以丢消息**：丢了只是晚一点看到，不会不一致。这也让服务端不必持有
任何"这条连接看到过什么"的状态。

### 决策三：在 `after_commit` 广播，不在路由里广播

**否决：每个写路由自己调 `publish()`。** 九十多个写路径，漏一个就是一处永远不刷新的
界面，而且不会报错。这类"漏一个就静默失效"的设计，这个项目已经在 ADR-035 里吃过一次亏。

**选择：`audit.record()`（所有写操作都会调用）在 session 上记一笔，
SQLAlchemy 的 `after_commit` 统一发出去。** 一个钩子覆盖全部写路径，而且天然保证
"回滚的事务不会发出提示"——从事务里推出去的提示是假的，客户端白刷一次之后就不再信这条通道了。

### 决策四：不用 `EventSource`，用 `fetch` + `ReadableStream`

`EventSource` 不能设置请求头，token 只能拼进 URL。URL 会进 nginx 访问日志、浏览器历史、
Referer。这个项目在别处已经为 `<img>` 开了 `?token=` 的口子（那些标签确实设不了头），
但新代码没有理由再开一个。

代价是三十行 SSE 帧解析和手写的重连退避——可控，而且顺带解决了 `EventSource`
不支持自定义重试策略的问题。

### 决策五：这条路径绕开 gzip

Starlette 的 gzip 中间件会把流式响应缓冲到 `minimum_size`（800 字节）才 flush。
心跳帧只有 12 字节，等于这条流在安静的时候永远不 flush——客户端看到的是"连上了但没反应"，
和功能坏了没有区别。所以 `StreamSafeGZipMiddleware` 对 `/events/stream` 直接放行。

**后果**

- 正面：两台设备之间的可见延迟从"最长 60 秒"降到几百毫秒（实测 320ms 左右）。
- 正面：本机模式完全不受影响（不建连），同步模式的 60 秒轮询退化成兜底。
- 负面：**进程内广播**。多 worker 部署时，A worker 上的写不会唤醒 B worker 上的连接。
  网关模式默认单进程，够用；真要多 worker，得把 `services/events.py` 的注册表换成
  Redis pub/sub。这一点写在模块注释和 API 文档里，不假装已经支持。
- 负面：自己的写入也会收到自己的提示，多一次空拉取。要区分就得给每条记录带设备号
  并在服务端过滤，为一个空请求不值得。

## ADR-038：界面按「壳」分叉，菜单栏画在页面里

**背景**：桌面端（Windows/macOS）要求把「扫码」改成「查询」并移除相机，移动端
（Android/iOS）保留扫码；同时要像桌面软件那样在左上角放一条菜单栏。

### 决策一：能力按 UA + Tauri 标记判断，不用构建期常量

同一份前端产物要同时跑在：Tauri 桌面壳、Tauri 手机壳、桌面浏览器、手机浏览器。
如果用 `import.meta.env` 或编译期常量分叉，就得为每个形态各打一份包——发布矩阵
立刻从 4 个变成 8 个，而差异只有"这一页要不要相机"。

**选择**：`lib/platform.ts` 用 `__TAURI_INTERNALS__` 判断是否在壳里，用 UA 判断
是否手机，得到 `desktop | mobile | web` 三种形态。桌面浏览器按桌面处理（笔记本
对着屏幕扫二维码本来就没意义）。

**后果**：手机浏览器访问网关时仍然是扫码，桌面浏览器是查询。这不是"桌面端"的
严格定义，但是同一台设备的合理行为。

### 决策二：桌面端的相机区块**不挂载**，不是隐藏

`display: none` 的 `<video>` 仍然是 DOM 的一部分，`startCam()` 一旦被调用
（快捷键、自动恢复、`?code=` 参数），`getUserMedia` 照样会申请摄像头权限。
用户看到的是一个没有相机界面的页面，却在系统层面被要求授权摄像头——比报错更难理解。

**选择**：`{!manualOnly && (<>…</>)}`，桌面端这段 JSX 根本不执行。

### 决策三：`/scan` 一个路由两种叫法

不新建 `/query` 路由：两边的数据流完全一样（一次 `scan/lookup` + 候选列表），
差别只在"有没有相机"和"标题叫什么"。开两个路由意味着两套页面状态、两处要同步
改的候选列表渲染，而它们永远不会分头演化。

### 决策四：菜单栏画在页面里，不用 Tauri 原生菜单

**否决：`tauri::menu`。** 它更像"真桌面软件"，但原生菜单只在壳里存在；浏览器版
就没有菜单，两套代码路径。而且原生菜单的回调要经过 IPC，做同样的动作得写两遍。

**选择**：`components/AppMenuBar.tsx`，一个固定高度的 HTML 条，用
`-webkit-app-region: drag` 保留拖动窗口的能力。三种形态共用一套实现，Web 端不渲染
（浏览器自己有 chrome）。

**菜单内容刻意避开一级导航**：文件（新建/打印/导入导出）、编辑（查找）、视图
（主题/重新加载）、帮助（数据目录/日志/快捷键）、关于（版本/关闭窗口/退出登录）。
物品、维护、设置这些已经在左侧栏里，菜单再放一遍等于给同一件事做两个入口。

### 决策五：打印机不假装能枚举

浏览器和 WebView 都没有"列出打印机"的 API，`window.print()` 一调就是系统对话框，
打印机在那儿选。所以 `lib/print.ts` 不去伪造一个设备列表，而是把"这一页怎么送到
打印机"抽象成三个出口：系统打印对话框、存成 PDF、新窗口兜底；各自写清楚它会干什么，
用户选一次就记住。

**后果**

- 正面：桌面端不会出现"点开是黑的相机"，也不会申请用不到的权限。
- 正面：打印标签从"全量导出"变成"挑完再生成，生成后再决定打不打"。
- 负面：桌面浏览器访问网关也失去了扫码。真要扫，用手机打开同一个地址即可。

## ADR-039：桌面壳里不要 Service Worker

**背景**：前端同时是 PWA（浏览器访问网关时要能离线打开），因此注册了 Service Worker
缓存界面资源。桌面壳复用了同一份产物，于是壳里也注册了。

**问题**：壳里的界面资源是**编进二进制**的，每次构建文件名都带新的哈希
（`index-s4qXB9Vc.js` → `index-Dk3mP1qA.js`）。而 SW 会把上一版的 `index.html`
缓存下来，它引用的那个文件名在新包里根本不存在。结果是窗口打开了、页面框架在、
**应用脚本一行都不执行**——白屏。更糟的是它自己好不了：每次导航都从缓存里拿那份
旧 HTML，永远不会触发更新。

1.0.6 就撞上了：用户从 1.0.5 升级，WebView 配置目录里的 SW 还在，直接白屏。
判据是 `IndexedDB` / `Local Storage` / `Cache` 的时间戳全都停在上一版，
只有 `Session Storage` 是新的——说明页面起来了，JS 没跑。

**决策**：两件事一起做。

1. 壳里不注册 SW（`main.tsx` 用 `isTauri()` 分流），并把已注册的注销掉。
2. Rust 侧在建窗口之前删掉 `EBWebView/Default/{Service Worker,Cache,Code Cache}`。
   第二步是给已经坏掉的配置目录兜底——JS 都跑不起来，改前端代码救不了它。

**否决：给 sw.js 加版本号让它自己更新。** 版本号确实能触发 `install → activate`，
但那套机制依赖"页面能正常加载"；白屏的时候页面根本没加载，更新逻辑没机会执行。

**否决：换 bundle identifier 换一个干净的 WebView 配置目录。** 那等于让用户丢登录态
和本地库。

**后果**

- 正面：升级不会再白屏；壳里的界面永远来自二进制，不存在"缓存里的旧版本"。
- 负面：每次启动多删三个缓存目录，首屏要多解析一遍 JS（几十毫秒）。
  界面资源本来就在本地，这个代价可以接受。
- 注意：浏览器/PWA 路径不受影响，SW 照常工作（已验证：壳内注册数 0，浏览器 1）。
