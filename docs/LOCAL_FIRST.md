# 本地优先与端到端加密同步

这份文档说明「数据放在哪」这件事。它不只是功能说明——它决定了几种失败方式，以及哪些失败是可以恢复的。

一句话版本：**每台设备都有一份完整数据，所有读写只跟本机打交道；服务器是可选的会合点，用来让多台设备的副本收敛，而不是数据的主人。**

---

## 1. 三种运行模式

设置在「设置 → 同步 → 数据存在哪里」，随时可切。

| 模式 | 数据在哪里 | 断网 | 多设备 | 适用 |
| --- | --- | --- | --- | --- |
| **仅本机** `local` | 本机 IndexedDB | 完全可用 | 不共享 | 一台设备，或先自己用起来 |
| **本机 + 加密同步** `sync` | 本机完整；服务器存轻型索引 + 密文 | 完全可用，恢复网络后自动补传 | 支持 | 手机 + 电脑，或一家人共享 |
| **直连服务器** `remote` | 服务器数据库 | 不可用 | 支持 | 没有本地存储的浏览器、只读终端 |

打包应用（桌面 / 手机）默认是第一种。浏览器默认是第三种，以免已经在用网关部署的人被无意切换。

模式是**每台设备的本地偏好**，不是家庭级配置。同一家人可以一台手机同步、一台旧平板只读直连。

### 服务器从哪来

三选一，互不冲突：

| 方案 | 怎么做 | 适合 |
| --- | --- | --- |
| **这台电脑** | 桌面应用设置 → 同步 → 「允许家庭内设备连接」，拿到 `http://192.168.x.x:端口` 填到手机上 | 家里只有一台常开的电脑 |
| **Docker** | `docker compose up -d`，见 [DEPLOYMENT.md](DEPLOYMENT.md) | NAS、迷你主机、长期开机的设备 |
| **云主机** | 同上，前面套一层反向代理和 TLS | 异地访问、远程协作 |

桌面端默认**不**监听局域网端口。打开它意味着同一 Wi-Fi 下的设备能看到登录页——这不是一个应该替用户做的决定。打开后传的仍然是密文：路由器看得到流量，读不懂序列号和照片。

## 2. 数据怎么分层

用户在一次同步里其实要求了两件相反的事：服务器要能派发数据（所以要能索引），隐私字段又不能被服务器读到。这两件事只能靠**字段级分层**同时成立。

每条记录被拆成两半：

```jsonc
{
  "entity": "item",
  "id": "…",
  "hlc": "…",              // 混合逻辑时钟，冲突时用它比新旧
  "meta": {                // 明文。服务器可读、可索引
    "id": "…", "code": "HL-000123", "name": "戴森 V12",
    "category_id": "…", "location_id": "…",
    "status": "in_use", "quantity": 1, "unit": "件",
    "brand": "Dyson", "model": "V12",
    "tags": ["家电"], "archived_at": null,
    "created_at": "…", "updated_at": "…"
  },
  "secret": "base64(nonce‖ciphertext)",   // 密文。服务器读不到
  "blobs": ["blob-…"]                       // 附件密文，单独存放
}
```

**明文**：名称、编号、分类、位置、状态、数量、单位、品牌、型号、条码、标签、时间戳。
这些是列表页、筛选器和「新设备配对后立刻能看到东西」所必需的。它们也确实是低敏感度的。

**密文**：描述、序列号、购买价格、购买渠道、购买日期、保修截止、自定义字段、备注、借用人联系方式，以及**全部照片与附件**。

这个切分是产品判断，不是技术限制。如果连「名称」也不能给服务器看，把设置里的 `privacy` 改成 `strict` 即可——那时 `meta` 只剩 `id`，新设备在输入口令前看到的是一个空列表但结构完整的库。

> 服务器端代码里没有任何解密路径：没有密钥、没有 KDF、没有回退分支。它拿到 `secret` 的方式和拿到一张图片字节流没有区别。

## 3. 本地库

`frontend/src/local/store.ts`。

**为什么是 IndexedDB 而不是 SQLite。** 同一份代码要跑在 Android WebView、iOS WebView、Windows/macOS/Linux 的 WebKit/WebView2，以及普通浏览器里。IndexedDB 是这些环境唯一都有的数据库。家庭数据量（几千条记录）全量放进内存毫无压力，所以磁盘层只需要负责**持久**，不需要负责**查询**——查询就是内存里的数组扫描。

四个对象仓库：

| 仓库 | 内容 |
| --- | --- |
| `records` | `{k: "items/<id>", v: row}` |
| `meta` | 设备身份、同步游标、密钥材料 |
| `blobs` | 附件原始字节（本机明文） |
| `outbox` | 待推送记录的 `k → hlc` |

写入是**写穿 + 合并刷盘**：内存立刻更新、界面立刻响应；40 ms 内的多次写入合并成一个事务。所有非 GET 的本地调用结束前会 `await flush()`，所以「新建物品后立刻刷新」不会丢。

每条记录带 `_hlc`（最后一次写入的混合逻辑时钟）和可选的 `_deleted`（墓碑）。墓碑不会删掉，因为「不存在」和「被删除」对一台离线设备来说是两件不同的事。

## 4. 同步协议

`frontend/src/sync/engine.ts` ↔ `backend/app/routers/sync.py`。

### 4.1 顺序：混合逻辑时钟

```
<10 位 base36 物理毫秒>-<3 位 base36 计数器>-<8 位设备后缀>
```

物理部分让时间戳仍然可读、可排序；计数器保证同一毫秒内的两次写入仍然有先后；接收远端时间戳时 `observe()` 会把本地时钟推到它之后，因此因果不会倒挂。字符串直接比较就是大小比较。

对时不准的手机不会把别人的修改盖掉——它只会把自己这次修改排在后面。

### 4.2 游标：每个家庭一个序列

服务器为每个家庭维护一个 `head` 计数器。每次接受一条记录就 `head += 1` 并写进 `sync_records.seq`。客户端拉 `GET /sync/pull?since=<cursor>`，只拿 `seq > cursor` 的记录。

用家庭内计数而不是全局自增，是为了不让游标本身泄漏「这台服务器上有多少个家庭、有多活跃」。

### 4.3 冲突：记录级 LWW + 字段级明文合并

推送时如果服务器上那条记录的 HLC 更高，服务器**保留自己的版本，并在同一个响应里把它还给你**（`resolved`），所以两台设备一次往返就收敛，不用等下一轮。

代价是记录级胜者通吃：A 改了价格、B 同时改了位置，最终只有一个人的改动留下。

这在家庭场景里是可以接受的取舍——同一件物品被两个人在同一分钟编辑的概率很低，而实现字段级 CRDT 的成本（每个字段一个时钟、合并规则、字段级删除语义）远高于它在这里的价值。真出现冲突时，`audits` 里能看到两次修改的痕迹，用户手动改回来即可。

### 4.4 删除

删除写墓碑（`op: "delete"`），不删行。墓碑随游标正常传播。一台离线一个月的设备回来时，会收到墓碑并把本地那条标记为删除，而不是「没收到所以还留着」。

### 4.5 附件

附件字节先于引用它的记录上传：`PUT /sync/blob/{id}` 存的是**客户端加密后的分块密文**，服务器只知道大小和 SHA-256。

拉取侧默认**不下载附件**——只同步元数据。用户点开某张照片时才 `fetchBlob()`：下载 → 解密 → 存进本机 `blobs` → 生成 object URL。一台只有 32 GB 的手机不应该为了同步一个家庭相册而先下载 4 GB。

## 5. 加密

`frontend/src/local/crypto.ts`。

### 5.1 为什么不是 WebCrypto

`crypto.subtle` 只在 secure context 下存在。Tauri 在部分平台把页面放在 `tauri://localhost` 这类自定义 scheme 上，Android WebView 里的局域网 `http://192.168.x.x` 更是明确不属于 secure context。依赖它意味着「在某些设备上加密功能直接不存在」——这是最糟的失败方式。

所以用纯 JS 实现：`@noble/ciphers` 的 XChaCha20-Poly1305 + `@noble/hashes` 的 Argon2id。两者都经过审计、无 WASM、无原生依赖，任何有 `Uint8Array` 的环境都能跑。

### 5.2 密钥层级

```
口令 ──Argon2id(salt, m=64MiB, t=3, p=1)──▶ KEK(32B)
                                            │
                          XChaCha20-Poly1305 │ 解封
                                            ▼
                                          DEK(32B) ──▶ 字段与附件
```

- **DEK** 随机生成，永不更换（除非主动轮换）。
- 服务器只保存 `salt` + `wrapped_dek`（KEK 加密后的 DEK）+ `verifier`。
- **改口令 = 用新口令重新包封同一个 DEK**，历史密文全部继续可读。这是「改密码」应有的语义。
- `verifier` 让设备能区分「口令错了」和「密钥材料损坏」，而不需要任何会泄漏信息的往返。

### 5.3 字段加密的绑定

每条密文的 AAD 是 `hl1|{entity}|{id}`。这意味着一条记录的密文不能被搬到另一条记录上——服务器即使想作恶，也无法把「A 物品的价格」伪装成「B 物品的价格」而不被 GCM 校验发现。

### 5.4 附件分帧

```
"HLB1" | chunkSize(4B BE) | [ len(4B) | nonce(24B) + ct ] *
```

1 MiB 一块，每块独立 nonce、独立 AAD（带块序号）。好处是：40 MB 的视频不需要在内存里存在两份；上传被截断时会在解密阶段明确报错，而不是得到一堆看起来正常的垃圾。

### 5.5 本机保存 DEK

设置里可以关。默认开启，理由写在 `StoredKey.dek` 的注释里：本机本来就存着同一批数据的明文，攻击者能读到 DEK 就能读到数据，多一层锁只是让用户每次刷新都输一遍口令。共享设备上应该关掉。

## 6. 配对流程

第一次把设备接上服务器：

```
设备 A（已有数据）                     服务器                      设备 B（空）
      │                                  │                            │
      ├─ POST /auth/register ───────────▶│                            │
      ├─ GET  /sync/key ────────────────▶│  {configured:false}        │
      ├─ 生成 DEK，包封后 POST /sync/key ▶│                            │
      ├─ POST /sync/apply（全量推送）────▶│                            │
      │                                  │◀── 登录 + GET /sync/key ───┤
      │                                  │                            ├─ 用口令解封 DEK
      │                                  │◀── GET /sync/pull ─────────┤
      │                                  │                            ├─ 解密、写库
```

两条分支：

- **服务器还没有密钥** → 这台设备生成 DEK，成为这个家庭加密的起点。
- **服务器已有密钥** → 用同一句口令解封。口令错了会在本地就失败（GCM 校验），不会上传任何东西。

### 加入时的一个细节

一台从没用过的设备，本地只有**种子分类和地点**。如果直接推送，服务器上会出现第二套「家电/数码/客厅」，每个家庭从此有两份同名分类。

所以 `linkServer` 在 `joined && 本地没有物品、没有审计、没有附件` 时先 `clearContent()`（保留家庭、用户、成员身份），再拉取。

有真实数据的设备不会被清空——那是用户明确选择的一次合并。但合并本身有个陷阱：两台设备都从同一份种子清单开始，拉取之后本机会同时存在两套同名分类（本地的和服务器来的，id 不同），每个下拉框都会出现两个「厨房」。

处理顺序是 `pull → mergeDuplicateCatalog → push`：

- 拉取**之前**先记下本机已有的分类/地点 id（拉取之后已经没有特征能区分「本来就有的」和「刚下来的」——两者都会被盖上本机家庭 id）；
- 拉取之后，对每个本地分类找同表、同名、同父节点的对手；
- 找到就让服务器来的那条胜出：指向本地那条的物品改指向它，本地那条**物理删除**（它从没上传过，留墓碑等于向服务器广播一个它不认识的 id）；
- 然后才推送，避免把重复项写进服务器再发回给所有人。

实测：一台已有 2 件物品的设备加入别人的家庭，合并 19 条重名分类/地点，最终 3 件物品、11 个分类、没有重复项，刷新后仍在。

## 7. 二维码贴纸指向哪里

贴纸是要贴到实物上、撕下来就废的东西。它指的东西必须比「当前这台服务器」活得久。

早期版本把 `homeledger://scan?code=HL-000123` 编进二维码。三个问题：扫的人得先装 App；换端口就全废；二维码把物品编号公开写在脸上，谁拍一张都知道你家有几件东西、编号排到多少。

现在的二维码里是一个**随机 token**：

```
http://192.168.1.10:8000/api/v1/public/q/hK3vQ8sT2mR9xLpA1cN7
```

- **不用装 App**。手机自带相机扫开就是一张网页，IOS 和安卓都一样。
- **只在家里能看**。服务器判断请求来源地址，非私网一律 403，而且拒绝页和不存在的 token 长得一模一样。
- **可以作废**。链接泄露了就点「作废」，签一个新的，贴纸重打一张——只影响这一件。
- **服务器平时不干活**。没人扫的时候它不占内存、不起线程；扫了才唤醒，页面每 5 秒心跳续租，人走了 90 秒后自己睡回去。

打印机打出来的那张纸，本质上是「一块指向服务器的门牌」。门牌不该记录房间里的东西，也不该因为换了门锁就作废。

细节见 [API.md 的公开扫码页](API.md#公开扫码页public)。

## 8. 会坏在哪里

写清楚，比让用户自己发现好。

| 情况 | 结果 | 能否恢复 |
| --- | --- | --- |
| 忘记同步口令 | 云端隐私字段永久不可读 | ❌ 这是端到端加密的定义。服务器没有后门，也没有备份 |
| 所有设备都丢了 | 同上 | ❌ 导出的 JSON 快照包含明文，是唯一的兜底 |
| 清除浏览器数据 / 卸载应用 | 本机库消失 | 重新配对后从服务器拉回；附件按需下载 |
| 两台设备同改一条记录 | 一条胜出，另一条被 `resolved` 覆盖 | 审计里有痕迹，手动改回 |
| 不同设备时钟相差很大 | 修改顺序可能不符合直觉 | 不会丢数据；HLC 保证有序，不保证符合人的直觉 |
| 服务器磁盘满了 | 推送失败，本地照常可用 | 清理后自动重试 |
| 令牌过期（14 天） | 同步暂停并提示重新输入账号密码 | 重新输入即可，本地数据不受影响 |

## 9. 验证

不是「应该能跑」，是实际跑过：

- `backend/tests/test_sync.py`：14 个用例，覆盖推送/拉取/幂等/冲突回传/墓碑/租户隔离/分页/超限/密钥生命周期/密文桶/重置确认。
- 浏览器内双设备实测（Playwright + 真实服务器）：
  - A 在**离线状态**创建物品，序列号 `SECRET-SN-777`、价格 16999；
  - A 连接服务器并推送；
  - B 全新配置加入同一家庭，**收到物品且序列号与价格正确解密**；
  - C 用错误口令加入 → `同步口令不正确`；
  - B 新建物品并同步，A 拉到；
  - 直接查询服务器 SQLite：`sync_records.secret` 里**搜不到**序列号、描述、价格，`meta` 里只有名称等明文索引字段。
- 桌面端（Xvfb 无头）：窗口直接加载打包前端，IndexedDB 落盘 45 条记录；重启后记录数不变（没有被重新播种）。
- 加入已有家庭（Playwright + 真实服务器，三个独立浏览器上下文）：
  - A 在本地建 2 件物品，B 先在服务器上注册并建家庭、推 1 件；
  - A 用同一账号加入 → `{joined: true, mergedCatalog: 19}`；
  - A 最终看到 3 件物品、11 个分类、**没有重名分类**，刷新后仍在。
- 桌面端当服务器（deb 包 + Xvfb 实机点击）：
  - 点「允许家庭内设备连接」后 `ss` 显示监听从 `127.0.0.1:47823` 变为 `0.0.0.0:47823`；
  - `curl http://172.24.0.2:47823/api/v1/system/health` → 200；
  - CORS 预检对 `http://tauri.localhost`（手机 WebView）和 `http://172.24.0.2:47823`（浏览器直连）返回 allow-origin，对陌生 Origin 不返回；
  - 点「关闭对外服务」后监听回到 `127.0.0.1`。
- 二维码跳转（`backend/tests/test_public_qr.py`，10 个用例 + 真机 Playwright）：
  - 内网来源扫码 → 200，页面含名称、位置路径、序列号；
  - `8.8.8.8` 来源 → 403，且页面文案与「token 不存在」完全一致；
